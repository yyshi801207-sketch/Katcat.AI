# Katcat.AI Windows desktop

Katcat.AI V1.0.2 uses product version `1.0.2`, app ID `com.sudotech.xiaojing-office`, install directory `Katcat-desktop`, and a separate Documents workspace. It does not import or overwrite Xiaojing Accounting data. Local unsigned Windows packages require only `DSH_DESKTOP_APP_ID=com.sudotech.xiaojing-office` in `.env.windows`; they omit mandatory-update policy metadata and update feeds. Signed builds retain release-policy validation.

Fresh installations default to `%LOCALAPPDATA%\Programs\Katcat-desktop`; existing Katcat installations upgrade at the GUID-registered location, including the earlier `xiaojing-office-desktop` directory. The installer footer uses the transparent Katcat.AI wordmark in `installer-company-source.png`. Each successful installation or reinstallation initializes the light theme once, as described under [user-data paths](#permanent-user-data-paths). Earlier workspace folders and session paths remain intact; the new default workspace uses `Documents\Katcat_Home` directly.

The private Electron deployment for Katcat.AI. It is distributed through the Windows installer rather than npm, starts the bundled Node runtime and Web profile, keeps the renderer isolated from Node, and presents the local Host in one Windows desktop window.

The application document, bundled assets, and top-level PNG, SVG, ICO, and Web manifest files are served from the packaged frontend before the Host starts. API requests, plugin bundles, and event streams are forwarded only after the authenticated Host is ready; they return 503 before readiness and are never treated as those static resources.

The main window displays the local Katcat.AI startup artwork alongside the companion before Host preparation begins. The transparent black-and-red cat-cutout wordmark is a separate layer above the paper artwork. A compact 2px warm-orange indeterminate progress line animates beneath the centered wordmark with localized startup status; reduced-motion preferences keep the indicator still. The complete artwork retains its aspect ratio, and Electron owns the window controls. The startup page remains in the same application document until the client renders its first interface; no extra delay or navigation is added. Saved companion visibility is respected. Closing or minimizing the startup window remains effective when initialization completes, and an explicit open restores it during startup.

Automation tasks are built into the Web application hosted by Desktop. New profiles select the shipped Web bundles without the retired experimental Schedule bundle. The Host's standard profile loader removes that retired declaration during upgrades while retaining other bundle selections, installed dependencies, user metadata, and explicit plugin overrides. Existing tasks remain; a new installation does not create or execute tasks by itself.

User-visible application names and messages use Katcat. Existing installation identifiers and durable data paths retain their compatibility values.

## Permanent installer identity

`identity.json` is the source manifest and `verify-desktop-identity.mjs` locks these compatibility identifiers:

| Field | Value |
|---|---|
| Package name | `@deepseek-ai/dsh-desktop` |
| App ID / AppUserModelId | `com.sudotech.xiaojing-office` |
| NSIS GUID | `ddf2b5a9-34d7-4a3b-8f09-71ca62b6f58f` |
| Installation directory | `Katcat-desktop` |
| Executable | `Katcat.AI.exe` |
| Product name | `Katcat.AI` |
| Installation scope | Current Windows user |
| Shortcut | `Katcat.AI` |

The “Manage dsh Command” menu registers the installed `resources/runtime/cli/bin` command directory after confirmation. Packaging derives the Windows executable name from `identity.json.executableName` and the macOS executable from `identity.json.productName`. The ASCII Windows batch command uses the bundled primary Node runtime to forward arguments and inherited standard streams to Electron Node mode without changing the console code page; it waits for the CLI's console-interrupt shutdown and preserves its exit status. The CLI joins its parent's console only when unattached; a missing parent console does not prevent background commands.

A fresh installation uses a two-stage branded setup flow. The welcome page presents the Xiaojing mark, a SUDO-green install action, and an optional inline parent-directory picker that appends `Katcat-desktop`; the installation page keeps the Xiaojing artwork, hides the stock NSIS details area, shows the real file progress, and then launches the application without a separate finish page. The welcome page carries the installation consent notice, while the internal-use notice, complete upstream license, and third-party notices remain bundled under `resources/legal`. During a fresh installation into a target directory that did not previously exist, closing or cancelling the progress page opens the native confirmation prompt. Confirming cancellation starts an external cleanup helper and exits with code `1602`; after the installer process stops, the helper validates the fixed installation-directory name and removes only the partial application, current-user installer records, and shortcuts. Cancellation is disabled when the target directory already existed. During an in-place upgrade, the welcome page can still be closed before replacement starts, but cancellation is disabled once file installation begins to protect the previous installation. User-data paths are never part of cleanup. An installer with the same identity reads the exact `InstallLocation` from the fixed current-user GUID, hides path selection, asks that installed application to exit for the update, and handles only processes whose executable is inside that exact installation root. Before invoking an earlier uninstaller, the same fixed-root helper removes only legacy program entries whose absolute paths exceed the old Win32 limit, preventing deep unpacked dependencies from being misreported as an application-close failure. The standard updater then replaces application files and refreshes shortcuts and uninstall metadata. Unrelated processes and protected user data are never scanned, terminated, or removed. Moving an installation still requires uninstalling and reinstalling.

The branded installer displays Katcat.AI and the supplied transparent cat-and-robot artwork at up to 480×400 pixels in an 820×680 window. Short screens reduce the window and artwork together, keeping the title, installation controls, and bottom consent notice visible. The installation page retains native NSIS layout and message handling instead of creating custom child windows or a private message loop. Run `powershell -File apps/desktop/scripts/prepare-installer-logo.ps1` from the repository root to regenerate the white-backed welcome and small bitmaps from `build/installer-robot-source.png` without stretching either character. The source matches the Katcat chat hero; installer bitmaps remain separate files. The black-and-white cat-cutout letter app icon supplies Windows executable, installer, shortcut, taskbar, tray, and browser favicon artwork.

Run `node apps/desktop/scripts/prepare-installer-icon.mjs` from the repository root to generate Windows icons from `build/installer-icon-source.png`. The generator crops the fixed 1254-pixel source to a 1074-pixel square around its white rounded tile, preserving the black letter and cat-shaped opening. The four Desktop PNG aliases use that crop; browser favicon/sidebar and download-page assets retain the complete original source. A changed source requires reviewing the crop before generation. Electron-builder's converter produces the multi-resolution `build/installer-runtime-icon.ico` from the native PNG. The executable and development About panel use `build/app-icon.png`; native windows, taskbar, and tray use `assets/windows-icon.png`. The installer and quit dialogs use the ICO, copied to packaged `resources/tray.ico`. The application opens the Katcat workspace directly; its first-use API-key guide is owned by the product plugin. DeepSeek account login, the native authentication welcome window, and account-driven window changes are not exposed.

After installing files, the installer copies its icon to `resources/katcat-icon-<sha256>.ico`, updates existing Desktop and Start Menu shortcuts to that content-addressed path, retains their AppUserModelId, and sends a path-specific Windows Shell update notification. A changed icon gets a new path even when the application version stays unchanged. This step also runs for silent upgrades and does not recreate links omitted by the upstream shortcut policy. A write failure offers Retry or returns exit code `2` instead of launching the application as a successful installation. It neither restarts Explorer nor deletes the system icon cache. `dist:win` generates icons and runs `verify:installer-shortcuts`, which compiles the production updater against isolated temporary shortcuts and checks changed artwork, repeated installation, omitted Desktop links, and locked-icon failure.

<a id="permanent-user-data-paths"></a>
## Permanent user-data paths

Electron pins `userData` before the single-instance lock to `%APPDATA%\Katcat-desktop`. The bundled Host uses its `harness` child as `DSH_HOME`. The ordinary Host starts in `%USERPROFILE%\Documents\Katcat_Home`, supplied through `XIAOJING_OFFICE_WORKSPACE_ROOT`. The personal build does not create a Finance workspace. The Electron directory dialog starts in `Katcat_Home` when an add action supplies no initial path; users can select another directory. The previous `%APPDATA%\@sudotech\xiaojing-office-desktop` directory is retained without automatic reads or imports. The [Models onboarding coordinator](../../packages/client/ui-settings-models/README.md#onboarding-coordinator) uses installation identity and usable-provider readiness to decide whether to show guidance. Uninstall retains Katcat user data; deleting the workspace does not remove sessions, settings, or usage records.

Every successful NSIS installation, including a same-version reinstall, writes a fresh GUID to `katcat-installation-id.txt` beside the executable. Before starting the Host, Desktop holds the profile lock and sets only `ui-theme.preference` to `light` for an unconsumed installation ID, then records that ID in `userData/desktop/installation-theme-id.txt`. Other settings, credentials, sessions, and usage data remain intact. Ordinary relaunches retain any subsequent theme choice. Desktop supplies the public, non-secret ID to the Host through `KATCAT_DESKTOP_INSTALLATION_ID`; builds without an installer marker keep their existing behavior.

The 0.2.1 RC2 `DesktopHostProcess` owns the loopback Host lifecycle and pins `DSH_CLIENT_BUILD_PROFILE=xiaojing`, so only the Electron shell loads the application and Xiaojing-only Host plugins remain active in packaged builds. The desktop exchanges the authenticated launch token for a Host cookie used by the companion state stream; users do not open a printed URL.

`user-data-contract.json` protects sessions, settings, credentials, agent presets, profiles, storage, legacy uploads, native image attachments, usage accounting, the dedicated browser-control profile, Weixin channel state, desktop-companion preferences, Electron Local Storage, and the Documents workspace. The installer has `deleteAppDataOnUninstall: false` and never addresses those paths. `verify-user-data-contract.mjs` exercises a synthetic 0.1.9 data set through application replacement and the current readers. It requires protected bytes to remain unchanged except for exact installation-owned Web profile migrations from retired file-upload bundle tuples, with or without ModLens, to the current Web template; it verifies the atomic flat-to-version-1 credential migration on a private copy without creating a plaintext backup, and checks session, credential, preset, settings, upload, storage, and accounting compatibility. The V3 session migration accepts the fixture's immediately pre-step user message without rewriting its source; this gate must pass before an upgraded desktop release. A release that changes another durable format must add an atomic migration and a previous-release fixture before this check may change.

Platform account-page browser storage uses Electron's `session.fromPath` at `sessionData/p/<SHA-256 in base64url>`, retaining the complete issuer/account digest while shortening Windows cache paths. Before opening an account's first Session, an existing `Partitions/dsh-platform-<SHA-256 in hex>` directory moves atomically to that account's new directory. Existing preferences and browser files are retained; simultaneous old and new directories cause an explicit error without overwriting either. Host login credentials and the existing authentication-cookie cleanup remain unchanged. Accounts without a stable identity still use memory-only storage.

## Development preview isolation

Source-only Electron previews may set `DSH_DESKTOP_PREVIEW_ROOT` to an empty temporary directory before starting the desktop package. Unpackaged runs then place both Electron application data and the Documents workspace below that root; packaged builds ignore the variable and retain the permanent paths above. This keeps development previews from reading or writing an installed user's data. Before creating a development window, the desktop verifies that the shared Client artifacts came from a complete Xiaojing build; a missing or incompatible record stops with an instruction to run `pnpm run build:xiaojing` instead of showing an official or incomplete interface.

## Desktop companion and tray lifecycle

The main-window preload enables the Web layout's 40px Windows caption row before the application renders. Conversation and plugin controls stay below the native window buttons; the transparent companion does not reserve a caption. Drag regions belong to the layout, without an injected overlay over interactive content. Companion drag coordinates are rounded to signed 32-bit integers with negative zero normalized to zero; out-of-range coordinates are ignored before reaching the native window.

The desktop creates a transparent, focusless Katcat desktop-pet window and a system tray when Electron becomes ready. The companion uses the `screen-saver` topmost level and restores its stacking order on show and once per second while visible, except during dragging or pending placement. It reapplies the topmost flag only when the flag is lost. Raising it does not activate it or take keyboard focus; closing it releases the refresh timer. Windows secure desktops such as UAC and the lock screen remain outside this behavior. The Host-side companion plugin reduces session, approval, and sanitized Weixin lifecycle events to a content-free global state; Electron maps idle, thinking, executing, approval, and success to five bundled transparent Katcat cat poses. Failure reuses the neutral idle pose with a failure message. A 12-frame transparent sprite sheet supplies intermittent blinking, tail wagging, and yawning while idle. Each frame uses its measured transparent gutters; the pet renders without an outer drop shadow. One timer advances frames only during each short action; task activity, reduced motion, and window teardown cancel it immediately. Task content is not exposed to either renderer.

The companion can be dragged across displays, defaults to 50% of the original character size, and exposes a 30%–100% size control in Settings. Every application launch and Reset position action center the character between the measured composer right edge and the main-window content right edge. The main preload reports CSS layout coordinates; Electron converts them to screen coordinates. During native main-window dragging or resizing, the companion stays still; after the interaction ends and geometry updates stop for 150 ms, it uses the latest layout once. Renderer zoom follows the same settling rule. While the main window is minimized, the companion keeps its screen position; restoring the main window resumes automatic placement. A manual companion drag disables following until Reset or the next launch. When the gutter cannot contain the visible character with padding, it moves above the composer. Before a composer mounts, the startup window uses a bottom-right fallback. A drag position is retained only during the current application run, including tucking and waking; a new launch ignores the previous run's position. When a visible companion is created during desktop startup, it waits until the main application interface has loaded, waits another three seconds, and then shows the two-line introduction “我是 Katcat， / 您的超级个人助理！” once for five seconds; an active task cancels or replaces the introduction immediately, and a later manual wake does not replay it. Idle gestures do not change Host task state or display task-status bubbles. Its scale and clamped work-area position are stored in `%APPDATA%\Katcat-desktop\desktop-companion\preferences-v1.json`; the status bubble follows the scaled character instead of remaining at the top of the transparent window. The companion returns to the main window's display when a saved monitor is unavailable. Tucking it destroys only its BrowserWindow, while the Host, active tasks, and Weixin channel continue running and the Settings page or tray can wake it again.

Closing the main window hides it to the tray instead of exiting. The minimize button keeps its normal taskbar behavior, a second application launch restores the existing main window, and the application and tray quit commands use the shared quit controller. It confirms interruption when active tasks, Weixin connectivity, or scheduled tasks indicate risk, then destroys the main window before stopping the Host so renderer event streams cannot reconnect during shutdown. Companion and Platform cleanup and Host exit are awaited before the application exits. The first background transition uses the shared notification controller; the companion owns the sole system tray. The renderer receives the eight product methods plus two narrow bridges declared by `src/preload-app.ts` (compiled as `lib/preload-app.cjs`): one chooses a directory and one opens an existing absolute workspace directory through Electron's OS shell. The main process validates the owning renderer and path before either operation; the renderer receives no Node, filesystem, arbitrary IPC, or BrowserWindow access.

## Built-in automation runtimes

Browser automation uses the [native Edge and Chrome connections](../../packages/xiaojing/xiaojing-browser-control/README.md#native-browser-connections). Edge is the default; an explicit Chrome request selects Chrome. Browser Control settings enable already-open tabs through the browser's remote debugging permission and connection approval, without extension pairing, port entry, or token entry. Managed connections provide separate browser profiles when the requested browser and device policy permit them. Windows application control uses Windows PowerShell 5.1 and the operating system's `System.Windows.Automation` API. End users do not install Node, a browser driver, PowerShell module, or a separate automation service.

Both capabilities are independent Cordis rows. A development overlay can disable either row, while the Xiaojing product composition enables both and tells every new agent session when they are available. Browser and Windows observations use session-owned opaque identifiers and expire after state changes. Protected actions request approval; explicit session authorization applies only to eligible observed operation and target classifications, while unclassified actions remain one-shot.

## Independent integration patches

`integration-patches.json` inventories desktop API-key environment isolation, profile runtime-shadow protection, and file-upload composer repair separately from the product brand plugin. rc.2 owns the writable credential UI; the desktop patch only removes inherited `DEEPSEEK_API_KEY` values before Host startup. The desktop identity check fails if an inventory entry disappears or its owned path is absent. This keeps upstream conflict review focused without pretending these patches are official Harness behavior.

## Release checks

The desktop package target builds the Xiaojing client profile and passes `--client-profile xiaojing` to DSH tarball packing. The packer checks both the exact public build values and the artifact digest; ordinary npm packing and publishing retain the official profile requirement.

Run the identity, user-data, and product-layer verifiers plus desktop-companion, real Edge, and Windows UI Automation tests before preparing the bundled runtime. A release also requires a fresh Windows install and an in-place upgrade from the previous installer on both default and custom paths. The installed application must retain sessions, credentials, presets, plugins, attachments, workspaces, accounting data, the dedicated browser profile, Weixin channel state, and desktop-companion preferences before an installer is published.

The 0.2.1 RC2 package target runs `smoke-packaged-runtime.ts` against the assembled application before it writes the release record. The smoke verifies the prepared DSH tree, the packaged executable and primary runtime, including native Office conversion outside ASAR.

## Shell settings and packaging

Electron reads `userData/desktop/settings.json` once at launch. The optional `updates.allowTestAuthPopupWindow` boolean defaults to `false`; absent settings are initialized without replacing an existing document, and malformed settings retain their bytes while startup uses the default. This preference controls test update authentication only and does not enable the official account Welcome flow in Xiaojing. Restart after changing it.

The packaged `dshDesktopUpdateChannel` selects `nightly` or `latest`; older manifests default to `nightly`. The selected channel accompanies update-policy requests alongside the bundled kernel version. A stable `latest` feed rejects prerelease builds. Packaging keeps the Xiaojing product identity independent of the kernel package version. Retained-build upload validation uses the retained original product version even after the checkout advances.

The upstream [packaging reference](packaging/README.md) describes machine presets and signed, unsigned and unnotarized outputs; the [Windows signing guide](windows-signing/README.md) owns hardware signing requirements. Xiaojing additionally requires the identity, data-retention and client-profile checks above. The upstream publication and CI examples target DeepSeek infrastructure; they do not authorize publishing Xiaojing artifacts to those services.

## Known limitations

- Signed release packaging uses the 0.2.1 RC2 updater and Windows signing pipeline; the explicit unsigned package command remains for local qualification only.
- In-place upgrades apply only to the same Windows user and cannot move the installation directory.
- The requested Edge or Chrome browser must be installed and permitted by device policy. Existing-tab access additionally requires its native remote debugging permission and connection approval; failures do not switch browsers.
- The built-in automation is semantic, not visual: it cannot operate pixel-only controls, CAPTCHAs, UAC, the secure desktop, or elevated applications.

<a id="release-versions"></a>
### Release versions

`identity.json.productVersion` owns the Xiaojing application version; workspace package versions identify the Harness engine. Unpackaged previews display the identity's product version in About and the product renderer; packaged applications display their packaged version. `DSH_DESKTOP_BUILD_VERSION` must extend the application version through the validated test prerelease format.

<a id="upload-updates"></a>
### Upload updates

Update upload requires a completed package record and explicitly configured release storage credentials; the supervised uploader records each PUT and final outcome locally. Uploading and public CDN readback are separate release operations.

<a id="windows-ev-signing"></a>
### Windows EV signing

Signed packaging requires the configured EV certificate, signing toolchain and signature-cache ownership checks. Unsigned local qualification does not perform hardware signing or authorize publishing a release.
